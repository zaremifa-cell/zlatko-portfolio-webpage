A separate persistent provider simulator makes network timeouts real. The Java API, PostgreSQL transactions, queue delivery and recovery logic execute online. Identity decisions, provider outcomes and money movement are simulated; no real payment details are required.

01 — THE PROBLEM

A timeout does not tell you whether money moved.

A client can repeat a request while a provider accepts the original payment but loses the response. The system must distinguish an unknown outcome from a decline, preserve the original operation and avoid a second financial effect.

TrustPay models CREATED, PROCESSING, UNKNOWN, SUCCEEDED and FAILED explicitly. A merchant-scoped idempotency key identifies the operation; changing its customer, amount or currency produces a conflict.

02 — CORRECTNESS

Make the financial invariants visible.

A PostgreSQL transaction-scoped lock serializes matching requests. The unique merchant/key constraint is a second guard. Final state changes lock the payment row and commit with a balanced debit/credit pair in the ledger.

Amounts use integer minor units. The database enforces equal positive debit and credit amounts in one currency, and one ledger transaction per payment. Repeated callbacks have no additional financial effect; contradictory results create a review case.

03 — RECOVERY

Design for the gap between two systems.

The transactional outbox records a payment and its event in the same database transaction. Docker Compose publishes to RabbitMQ with publisher confirms; the online demo uses a private adapter and Vercel Queues. Duplicate delivery is expected and handled through event receipts and independent ledger uniqueness.

A crash after recording PROCESSING can leave the external result unknown. Reconciliation queries the provider with the original payment ID and safely completes the local transaction. In the RabbitMQ deployment, poison messages retry with backoff and route to a durable dead-letter queue.

JWT authentication, merchant ownership checks, an independent operations role, authenticated provider callbacks and payment audit records define the demo’s access boundaries.

04 — VERIFIED BEHAVIOR

Test the failures, then keep the evidence.

  • 20 simultaneous requests with one key create one operation.
  • Concurrent and repeated callbacks produce one balanced ledger posting.
  • A stopped RabbitMQ leaves a recoverable outbox record.
  • Replaying the actual broker event does not duplicate accounting.
  • SIGKILL during PROCESSING recovers the original payment after restart.
  • Provider timeout resolves through lookup instead of a new payment.

Nineteen PostgreSQL Testcontainers tests cover payment correctness, demo isolation and cloud queue retries, with zero skipped tests. Five additional Node adapter tests check the queue publisher and consumer HTTP boundaries. The repository includes the live demo, fault-injection scripts, captured results and a GitHub Actions workflow.

05 — THREE LIVE SCENARIOS

Different outcomes. Visible evidence.

All three scenarios were exercised through the public demo on 17 October 2026. The final status, queue receipt and ledger transaction count were also checked directly in PostgreSQL.

  • Successful payment — €100. The provider accepts the payment. The result becomes SUCCEEDED, with exactly one ledger transaction containing balanced debit and credit amounts.
  • Declined payment — €13. The provider deliberately rejects the payment. The result becomes FAILED, with zero ledger transactions. A decline is a tested business outcome, not an application error.
  • Delayed payment — €99. The provider durably accepts the original payment but delays its response. The result passes through UNKNOWN and then recovers to SUCCEEDED through provider lookup, with exactly one ledger transaction and no second payment.

All three events were published and consumed.

06 — REVIEWER WALKTHROUGH

Run the demo in a few clear steps.

  1. Open the live demo. Follow the button at the top: start a session, create a simulated customer, then verify the identity. No registration or personal information is required.
  2. Choose one of the three cards: Successful payment (€100), Declined payment (€13), or Delayed payment (€99). Try them one after another. The result panel shows progress, the final outcome and the ledger evidence automatically.
  3. Use the additional checks in the same upper workspace to repeat a request, repeat settlement, test an unverified identity or check merchant isolation. Repeating a request preserves the payment ID; repeated settlement must preserve one ledger transaction. An unverified identity is rejected with HTTP 422; another merchant cannot read the payment and receives HTTP 404.
  4. Inspect the technical API responses below the workspace. They show the actual HTTP status codes and JSON returned by the backend.

The isolated merchant session lasts 15 minutes and permits up to 3 customers and 25 payments. First requests may take longer after an idle period. If the session expires, start a new one.

07 — DEPLOYMENT BOUNDARIES

One payment core, two delivery environments.

The online sandbox runs the Java 21 / Spring Boot API on Vercel, uses PostgreSQL for durable state and accounting, and connects private Node queue adapters and a persistent Python provider simulator. Docker Compose runs the same payment and ledger core with RabbitMQ and scheduled background recovery jobs.

In the cloud demo, status checks also retry pending outbox publication and reconcile stale or unknown payments. There is no always-running reconciliation daemon or scheduled outbox scan in this profile: an unchecked pending payment can remain pending until its status is requested.

JWT authentication, merchant ownership checks, authenticated internal calls and callbacks, database constraints and audit records provide inspectable safeguards. Public demo sessions have restricted privileges; request limits are per instance.

08 — PERFORMANCE & OPERATIONS

Explain the plan, not just the number.

On 100,000 synthetic records, the same listing query measured 43.697 ms with a parallel sequential scan and 0.054 ms with the merchant/timestamp index. Measured locally; not a production capacity claim.

A JVM Flight Recorder session, HTTP latency measurements, EXPLAIN ANALYZE plans and an operations runbook accompany the source. The design keeps external payment I/O outside database transactions and documents the outbox publisher’s lock-duration tradeoff.

It is a portfolio reference with simulated identity and payments — not a certified gateway. Its emphasis is inspectable backend behavior under failure.

09 — RUN IT

Try it online. Inspect it locally.

Open the interactive demo and start an isolated 15-minute merchant session. Test the identity gate, successful and failed payments, duplicate requests, timeout recovery and merchant isolation. The cloud deployment runs Java on Vercel with PostgreSQL and Vercel Queues.
