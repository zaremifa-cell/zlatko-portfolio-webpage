One manifest. Four passes.

IMPLEMENTED PIPELINE
  1. 01 / LOADYAML splitter

    Files, directories or stdin. Each document keeps the line it starts on.

  2. 02 / TYPEserde PodSpec

    Workloads become Rust structs; unknown fields are ignored, missing ones defaulted.

  3. 03 / CHECK20 rules

    A static table of function pointers. Every resource meets every rule.

  4. 04 / REPORTTerminal · JSON · SARIF

    Exit code 0, 1 or 2 decides whether the pipeline continues.

No cluster access, no network calls and no unsafe code. Secret values are detected but never written into a report, a log or a SARIF file.

01 — THE PROBLEM

Most cluster breaches start as one line of YAML.

A container marked privileged: true, a password typed straight into an environment variable, a service account bound to cluster-admin. Each passes code review easily because it looks like ordinary configuration, and each gives an attacker a short path from one compromised pod to the whole node or cluster.

kubesieve checks manifests where they are cheapest to fix: in the repository, before deployment. It runs in milliseconds without a cluster, so it can sit in every pull request.

02 — WHAT IT CHECKS

Kubernetes semantics, not string matching.

  • Workloads — 15 rulesPrivileged mode, privilege escalation, root user, host namespaces, hostPath, dangerous capabilities, seccomp, writable root filesystem, mutable image tags, resource limits.
  • RBAC — 3 rulesWildcard verbs and resources, bindings to cluster-admin, read access to Secrets.
  • Network — 2 rulesServices exposed through NodePort or LoadBalancer without source ranges; Ingress without TLS.

Rules follow the kubelet’s own logic. A container’s securityContext overrides the pod’s; runAsUser: 1000 satisfies the non-root rule on its own; registry:5000/app is recognised as a port, not a tag. Mounting /var/log is high severity, mounting the container runtime socket is critical.

Pods, Deployments, StatefulSets, DaemonSets, Jobs and CronJobs are all understood, including init and ephemeral containers, and kind: List output from kubectl is expanded.

03 — RUST DESIGN

Let the type system hold the rules together.

Each rule is a Rule struct: metadata plus a plain function pointer. All twenty live in one static table, so adding a rule is one function and one table entry — no runtime registration, no allocation. An Emitter fills in file, line, resource and rule details, so each check only states where the problem is and what it is.

Output formats implement a Reporter trait and are chosen at runtime as trait objects. The pod specification is deserialised with serde into typed structs, so workload rules are checked by the compiler; simple one-field checks read the raw YAML tree instead.

Documents are split by hand rather than by the YAML library, so every resource keeps its starting line. A broken document becomes an error with exit code 2 while every other document is still scanned. SARIF fingerprints use FNV-1a instead of the standard library hasher, whose output is not guaranteed to stay the same between Rust releases.

04 — VERIFIED BEHAVIOR

Test the edges, not only the happy path.

  • A fully hardened Deployment produces zero findings, down to the info level.
  • Container settings override pod settings; only the overriding container is reported.
  • The Docker socket is critical, an ordinary host directory is high.
  • Passwords and AWS keys are found, and never appear in the output.
  • Invalid YAML, a missing file or an unknown rule id exits with code 2.
  • The JSON summary adds up; every SARIF result points to a valid rule index.

Nineteen unit tests cover the loader, the rules and the engine; eleven integration tests run the compiled binary as CI would — exit codes, stdin, file output and report formats. Clippy runs with warnings treated as errors.

05 — CI / CD

The tool gates its own pipeline.

GitHub Actions checks formatting, Clippy and tests on Linux, macOS and Windows, confirms the minimum supported Rust version and builds the Docker image. The same workflow then scans the repository’s example manifests and uploads the SARIF report, so findings appear as code-scanning alerts on GitHub — the way a team would use kubesieve on its own infrastructure.

Tagged versions build release binaries for Linux (static musl), macOS and Windows. The Docker image is a static binary in a distroless, non-root base.

06 — BOUNDARIES

Say what it does not do.

Findings point to the line where a resource starts and name the exact field as a path, not the field’s own line. Kustomize patches and Helm templates should be scanned after rendering, since a partial patch does not describe the final object. kubesieve is a static check of configuration, not a runtime security tool or a replacement for admission control.

The project was built with AI-assisted tooling; the design decisions, rule semantics and test cases are documented in the repository.

07 — RUN IT

One command, no cluster needed.

cargo install --git https://github.com/zaremifa-cell/kubesieve
kubesieve scan k8s/
helm template ./chart | kubesieve scan -
kubesieve scan k8s/ --format sarif --output kubesieve.sarif

Requires Rust 1.88 or newer. The repository includes deliberately insecure and fully hardened example manifests for a quick comparison.
